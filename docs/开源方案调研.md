# 开源方案调研：剧本 / 图片 / 视频 / 剪辑四环节

> 目的：回答「有没有成熟的开源项目或 Skill 可以直接复用到小程序里」。
> 约束：服务端**零第三方运行时依赖**（Node ≥ 22 ESM），不引入 Python / Java / npm 包；
> 因此结论分三类：**可直接借鉴流程**、**只借提示词与词表**、**不采用**。
> 调研时间：2026-11-05

---

## 一、结论速览

| 环节 | 最值得看的开源项目 | 结论 | 我们怎么用 |
|---|---|---|---|
| 剧本创作 | **Drama Skills**（zenstory-ai，11 个 Agent Skill）、**MovieAgent**（NUS Show Lab）、**FilmAgent**（哈工大深圳） | 借流程，不引代码 | 分层事实文件 + 分步门禁 + 互评校验，落到 `OneShot` 编排节点 |
| 图片生成 | **aid-studio**、**huobao-drama**、**WeiMeng**（均国产 AI 漫剧平台）、**Seedance Prompt Library** | 借资产模型与词表 | 资产库/连续性锁已有；补 `cinema_grammar.json` 词表 |
| 视频生成 | 同上 + **ViMax**（港大，导演/编剧/制片/生成四合一） | 借约束，不引代码 | 「首帧生视频最稳」「按模型能力校验分辨率/时长/比例」我们已实现 |

## 二、剧本创作环节

### 2.1 Drama Skills（最贴近我们的形态）

一套装进 Claude Code / Codex 的 11 步 Agent Skill，从原著到成片：`short-drama`（路由）→
`novel-analyze` → `develop` → `write` → `assets` → `image-prompts` → `storyboard` →
`video-prompts` → `produce` → `edit` → `review`。

它最值得抄的不是提示词，而是**三条工程约束**：

1. **五份 Markdown = 创作事实**：`剧本.md`（发生什么）、`视觉设定.md`（造型锁）、`分镜.md`（每镜起止 + 冻结关键帧）、`图片提示词.md`、`视频提示词.md`，剪辑时多一份 `剪辑单.md`。
   → 我们对应：`story_outlines` / `continuity_locks` / `director_plans.storyboard` / `compileRequest` / 本轮新增的 `edit_plan`。
2. **先预览、明确确认、再调用外部接口生产**——因为生图生视频按 token 计费，写错就是烧钱。
   → 我们对应：`/api/oneshot/quote` 先报价，`OneShot` 每步产出后停在待确认态。
3. **剪辑单逐刀写「画面发生了什么」，字幕逐字取自剧本**——不靠 ASR 猜。
   → 我们对应：本轮 `Subtitle` 直接用剧本对白 + 分镜时长生成 SRT，不做语音识别。

### 2.2 MovieAgent / FilmAgent（导演决策的结构化）

- **MovieAgent**：分层 CoT，流程是「剧本拆解 → 场景规划 → 镜头设计 → 摄影参数」，
  镜头设计内部再固定为「**先定景别 → 再定构图 → 最后定运镜**」。
- **FilmAgent**：导演/编剧/摄影多 Agent，用 `Critique-Correct-Verify` 与 `Debate-Judge` 互相挑错。

对我们的价值：

- 前者印证了 `DirectorPlan` 里 `shot_card → camera_move` 的先后依赖是对的（不能先定运镜再凑景别）；
- 后者对应我们已有的 `DirectorPlan.selfCheck()` + `RhythmMaster.gate()`——只是我们叫「自检」，
  等价于单 Agent 的 Critique 轮。**缺口是多一轮**：目前只检错，不重写。

> 不采用原因：两个项目都依赖 Python + LLM 编排框架 + （FilmAgent）3D 虚拟空间，
> 与零依赖 Node 服务端不兼容；且它们的产出是论文级 demo，不是可运营系统。

### 2.3 ViMax（长剧本与一致性）

港大开源，主打「长剧本 RAG 拆分 + 参考图保一致性 + VLM 校验首帧」。
我们的 `SeriesService` + 连续性锁 + `AssetLibrary` 已覆盖前两项；VLM 校验首帧属于增值项，暂不做（要额外的多模态调用成本）。

## 三、图片生成环节

### 3.1 三个国产开源平台的共性（aid-studio / huobao-drama / WeiMeng）

拆完它们的 README 会发现能力清单高度一致，说明这是行业收敛做法：

1. **先建资产库再分镜**：角色/场景/道具独立成库，分镜只引用资产 code；
2. **参考图占位协议**：提示词里用占位符引用角色参考图，按模型能力（支持几张参考图）安全编排；
3. **风格快照**：项目级风格锁定，避免第 3 集画风漂移；
4. **模型能力校验前置**：分辨率/时长/比例在报价阶段就按模型能力校验，不合法直接拒绝。

我们已全部具备（`AssetLibrary` / `CompiledRequest.assetsSnapshot` / `style_snapshot` / `validators.js` 12 校验）。
**不需要改架构，只需要补词表。**

### 3.2 提示词结构（词表来源：Seedance Prompt Library 等）

行业收敛的六段式：

```
[主体] + [景别] + [运镜] + [光影] + [情绪/氛围] + [画质/镜头参数]
```

我们 `segments.js` 目前是：`global（风格+导演+画幅+时长+画质+情绪）` + `lighting` + `transitionSound` + `negative`。
**缺两段**：`lens/atmosphere`（镜头参数：35mm、anamorphic、film grain、volumetric）与 `composition`（构图：对称、三分、框中框）。

→ 本轮在 `cinema_grammar.json` 里补齐，并在 `PromptCompiler` 增补这两段，顺序固定为
`主体 → 景别 → 运镜 → 构图 → 光影 → 氛围 → 画质`，与模型的实际理解顺序一致。

## 四、视频生成环节

两个被反复验证的工程结论：

1. **首帧生视频（image-to-video）比文生视频稳定得多**——aid-studio、FilmAgent、huobao-drama 都把首帧作为主路径。
   我们的 `ShotService` 已经**强制**「没有关键帧不许出视频」（409 `SHOT_SOURCE_REQUIRED`），方向一致。
2. **视频参数必须按模型能力校验**，不能前端随便传 1080P/16:9 就去调。
   我们的 `model_registry` + `validators` 已是这个思路。

→ 视频环节**不改架构**，只补「首尾帧」标记位（`first_frame_url` / `last_frame_url`），为后续接首尾帧模型留口。

## 五、剪辑成片环节

### 5.1 FFmpeg（唯一渲染路径）

`xfade`（转场）、`concat`（拼接）、`loudnorm`（-16 LUFS 归一）、`subtitles`/`ass`（字幕烧录）、
`amix` + `sidechaincompress`（对白闪避 BGM）——我们 `Renderer` 已覆盖前四项中的三项，
**缺字幕轨与 SFX 轨**，且 `xfade` 的 offset 计算不是累计值（多段链式会错位），本轮一并修。

### 5.2 pyJianYingDraft（剪映草稿导出）

能力很全：轨道/片段/转场/关键帧/音量淡入淡出/**导入 .srt 生成字幕**/批量导出。

但它有三个硬伤，**不适合放进服务端**：

1. Python + 依赖，破坏零依赖约束；
2. 剪映 6+ 对 `draft_content.json` 加密，模板模式失效；7+ 移除了自动导出所需的 UI 控件；
3. 只能在 Windows 版剪映下导出，Linux 容器里生成了也没用。

→ **采用它的「可编辑」思路，不采用它的实现**：我们额外导出
`剪辑单.md` + `字幕.srt` + `素材清单.csv`，用户想手工二创时直接拖进剪映，30 秒重建时间线。

### 5.3 Whisper（自动字幕）

我们**不需要**：剧本对白是已知文本，按「字数 / 语速」分配时间码比 ASR 更准，还省一次模型调用。
Whisper 只在「用户上传成片要做字幕」时才需要，不在本轮范围。

## 六、无版权音乐与音效

| 来源 | 授权 | 商用 | 署名 | 有 API | 结论 |
|---|---|---|---|---|---|
| **Pixabay Music** | Pixabay Content License（CC0 式） | ✅ | 免署名 | ❌（API 只覆盖图/视频） | ✅ 主库 |
| **Mixkit** | Mixkit Free License | ✅ | 免署名 | ❌ | ✅ 备选（条款排除 CD/游戏/广播电视） |
| **FreePD** | CC0 | ✅ | 免署名 | ❌ | ✅ 备选 |
| **Free Music Archive** | 逐曲不同（CC0 / CC-BY / NC） | 逐曲 | 多数要 | ❌ | ⚠️ 需逐首核对，不做默认库 |
| **Incompetech** | CC-BY 4.0 | ✅ | **必须署名** | ❌ | ⚠️ 可用但要写入片尾 credits |
| **Jamendo** | CC（商用需另授权） | ❌ 需购买 | — | ✅ | ❌ 不采用 |

**关键发现**：我们 `bgm_library.json` 里 12 条曲目全部是 `_status: TEMPLATE_NEED_REAL_ASSET`，
`local_path` 是 `cos://bgm/...` 这种占位路径——**库里没有一条真实音频**。
这意味着「每次生成视频自带 BGM」目前是假的，必须解决。

→ 三级兜底（本轮实现）：

1. **用户上传**自己的 BGM（最稳，版权自负，需勾选授权承诺）；
2. **AI 生成**（`MUS-DEFAULT` / `AUTO-SUNO-V6` 已在模型注册表里），live 模式走中转站；
3. **程序合成**（`SynthBGM`，零依赖生成 WAV）：按情绪/BPM/调式合成 pad + bass + pulse，
   **100% 无版权、零成本、离线可用**，作为永远能兜住的那一层。

音效（SFX）同理：转场 whoosh / riser / impact、环境音 bed，用同一合成器出，按转场类型与情绪自动排点。
