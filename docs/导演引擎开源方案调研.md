# 导演引擎开源方案调研与优化落地（V4.17）

> 目的：回答「后台导演引擎能不能直接换成一个功能齐全的开源实现 / Skill」，以及在不引入任何第三方运行时依赖的前提下，从这些方案里能拿走什么。
> 约束沿用 `docs/开源方案调研.md`：服务端**零第三方运行时依赖**（Node ≥ 22 ESM），不引 Python / Java / npm 包；只借**方法论、数据结构、判据词表**，不搬代码。
> 调研时间：2026-11-08

---

## 一、结论速览

**没有可以直接替换的方案。** 市面上的开源项目分两类：

1. **Agent Skill 类**（把 Claude Code / Codex 当创作助手）：能产出九列分镜表、能审稿，但**没有服务端 API、没有落库、没有版本与成本控制**，本质是"人坐在终端里用"，无法嵌进小程序的后台任务队列。
2. **平台类**（国产 AI 漫剧平台）：功能齐全但都是 **AGPL / 无 LICENSE / 商用受限**，且技术栈是 Python + 前端重型框架，与本项目零依赖前提冲突。

所以本轮的结论是：**继续自研引擎，把开源方案里的"判据"和"列定义"补进来**，一共补了四处真实缺口。

| 开源项目 | 许可证 | 能拿什么 | 我们怎么用 |
|---|---|---|---|
| `Shanyin-ai/shanyin-director-master` | MIT | **九列分镜表**列定义 + 551 个镜头的人工时长统计与基准 | 补齐分镜第 9 列「叙事目的」；用它的时长分布校准我们的区间表 |
| `A-cat-with-carrots/OnlyShot` | MIT | **17 类视频生成失败模式**清单（首尾帧漂移、多手多指、服装突变……） | 转成镜头语法体检的判据项 |
| `zenstory-ai/drama-skills` | MIT | 11 步 Skill 流水线与"创作事实文件"分层 | 已在 V3.x 借鉴；本轮借它的**定调（brief）先行**顺序 |
| `Vi7QY/screenwriter-skill` | MIT | 38 条审稿规则（钩子/密度/反转位置） | 抽成节奏与语法判据，未新增模块 |
| `mengxiujie/ManjuForge` | MIT-0 | **22 项一致性检查**清单 | 与本项目五维一致性守卫对照，确认无遗漏 |
| `huobao-drama` / `aid-studio` / `WeiMeng` | AGPL / 无 LICENSE | 资产模型、提示词词表 | **不采用代码**，仅作名词对照 |
| `ViMax`（港大） | 无 LICENSE | 导演/编剧/制片/生成四合一架构 | **不采用**，仅参考分层思路 |

> 许可证红线：AGPL 与 CC BY-NC-ND（禁止演绎、禁止商用）在本项目里是**直接排除**，
> 连"改写后使用"都不行。凡是没写 LICENSE 的仓库，一律按"保留所有权利"处理。

## 二、诊断：引擎原来到底缺什么

在动手前先把病灶列清楚，避免"抄了个热闹"。

| # | 病灶 | 现象 | 后果 |
|---|---|---|---|
| 1 | **整集等长** | 总谱给了节奏位（黄金三秒 / 反转落点），但分镜时长按 `集时长 / 镜数` 平分 | 前 3 秒不快、反转不给重量，**节奏落不了地** |
| 2 | **没有统一定调** | 风格预设、导演档案、题材各自被不同环节读取 | 编剧理解的"冷峻"和出图理解的"冷峻"不是一件事 |
| 3 | **分镜只有 8 列** | 缺「叙事目的」 | 剪辑与审稿时无法回答"这一镜为什么存在" |
| 4 | **没人管剪辑顺不顺** | 一致性守卫只管"人和物崩没崩" | 画面都对，剪起来还是跳、还是平 |

对应四个新模块：`ShotTiming` / `DirectingBrief` / `ShotGrammar` / `PromptBudget`。

## 三、ShotTiming：把节奏落到秒

**开源依据**：`shanyin-director-master` 的 551 镜统计显示，短剧单镜时长集中在 **2~5 秒**，
且**叙事功能不同的镜头，时长分布显著不同**（钩子镜普遍 2~3.5s，反转镜普遍 5~7s）。
这直接否掉了"平均分配"。

### 3.1 九种叙事目的与区间

| 目的 | 标签 | 区间(s) | 为什么是这个长度 |
|---|---|---|---|
| `hook` | 开场钩子 | 2–3.5 | 前三秒决定划不划走，必须快而炸 |
| `establish` | 交代/建立 | 3.5–5 | 先让观众看清空间与关系，信息要读得完 |
| `advance` | 推进/升级 | 2.5–3.5 | 事件在加速，镜头也要加速 |
| `present` | 展现/呈现 | 4–5 | 标准叙事镜，给足读取时间 |
| `mood` | 情绪/氛围 | 4–5.5 | 氛围需要呼吸，不能一剪就走 |
| `turn` | 转折/翻转 | 5–7 | 翻转的重量要落地，太快会像没发生 |
| `empathy` | 共情/沉淀 | 5–8 | 观众需要时间站到角色那一边 |
| `echo` | 呼应/闭环 | 4–5 | 要让观众认出这是前面的伏笔 |
| `endHook` | 集末钩子 | 3–4 | 留一个未解的问题，但不能拖 |

**关键设计**：节奏库的 `purpose` 是**结构位置**（"黄金三秒""反转落点"），
叙事目的是**这一镜在全片里干什么**（交代/推进/转折）。两者混用会出现"集末钩子被当成升华给到 10 秒"。
所以 `functionOf()` 单独做一层翻译，不直接透传。

### 3.2 分配算法（三阶段）

```
① 区间体检   lo/hi = 叙事区间 ∩ 景别 len_hint ∩ [1s, 10s]
             镜数少、集时长长 → relaxHigh（放开 10s 上限，按比例摊，而不是让整集短 40%）
             镜数多、集时长短 → relaxLow（允许压到 1s，按比例压，否则永远减不下去）
② 水位法     24 轮迭代，每轮把超出区间的部分按剩余容量回灌，直到总和 == 集时长
③ 补偿       最后差额给"最不敏感"的那一镜，避免出现 0.3s 的碎渣
```

**硬边界**：单镜 1–10s（视频模型单次生成上限 10s；<1s 会被看成闪帧）。

### 3.3 可量化的产出

`stats.timing` 里带三个指标，直接进 `plan.stats`：

- `total`：实际总时长（必须等于集时长）
- `contrast`：`max / min` 快慢对比。**旧实现每镜等长，这个值恒为 1.0**——本轮修的就是这个病
- `fast_ratio`：≤2.5s 的快切占比

`validate()` 里加了 `contrast < 1.5` 的告警：整集快慢差不到 1.5 倍，观感就是"平"。

## 四、DirectingBrief：一次定调，全链路引用

**开源依据**：`drama-skills` 的第一步不是写剧本，是产出一份**所有后续环节都要读的事实文件**。
它的价值不在内容，在于"只有一份"。

`DirectingBrief.build()` 输出 8 段确定性结论（同样的项目输入 → 同样的 brief，不含随机）：

| 字段 | 内容 |
|---|---|
| `tone` | 风格 × 导演的一句话定调（如"冷峻写实 × 强情绪特写"） |
| `one_liner` | 一句话说清"这片子看起来是什么样" |
| `theme` | 主题（取自 outline 的 logline，缺失时退回标题） |
| `color` | 主色/辅色/强调色三个角色，各带用途 |
| `camera` | 覆盖策略（远景交代几镜、中景推进几镜、近景给情绪几镜） |
| `cut` | 剪辑倾向（平均镜长、快切比例、转场偏好） |
| `sound` | 声音策略（有无 BGM、环境声密度、静音留白） |
| `avoid` | 明确不要的东西（避免"什么都想加"） |
| `checkpoints` | 3–5 个可验收的检查点 |

落在 `director_plans.plan.global.directing_brief`，`DirectorAgent.brief(projectId)`
优先读已存的 plan，没有就用同样的规则现场推导（`derived_from: 'derived'`），
保证"没生成过也能看到定调"。

## 五、ShotGrammar：管剪起来顺不顺

**开源依据**：`OnlyShot` 的 17 类失败模式里，有相当一部分**不是生成失败，是剪辑失败**
（连续同景别、跳轴、快切后不给呼吸）。这类问题一致性守卫完全看不见。

`auditEpisode()` 的 11 类判据：

| 代码 | 级别 | 判据 | 修法建议 |
|---|---|---|---|
| `DURATION_OVER` | error | 单镜 > 10s | 拆两镜，或改镜头内推拉 |
| `DURATION_UNDER` | error | 单镜 < 1s | 并到相邻镜 |
| `REPEAT_CARD` | warn | 连续 3 镜同卡 | 换同叙事的景别/角度 |
| `REPEAT_MOVE` | warn | 连续 3 镜同运镜 | 中间插固定或反向运镜 |
| `DISTANCE_STUCK` | warn | 连续 4 镜同景别 | 按"远→中→近"覆盖一遍 |
| `JUMP_CUT` | warn | 景别跳级 + 硬切 | 补过渡镜或换转场 |
| `NO_ESTABLISH` | warn | 前 3 镜无远景/全景 | 开场先给环境 |
| `NO_BREATH` | warn | 连续快切后无长镜 | 快完给一镜呼吸 |
| `NO_CONTRAST` | warn | 最快/最慢 < 1.5 倍 | 拉长情绪镜、压缩推进镜 |
| `CLOSEUP_OVERLOAD` | warn | 特写占比过高 | 补中景承接 |
| `END_NO_FREEZE` / `TRANSITION_DROUGHT` | info | 集末无定格 / 8 镜以上全硬切 | 提示，不拦 |

打分：`error` 扣重、`warn` 扣中、`info` 扣轻 → **A / B / C / D** 四档。
`DirectorAgent.overview()` 直接把 `grammar` 段落带给前端，导演页不需要额外请求。

## 六、PromptBudget：别把预算花在废话上

**开源依据**：`huobao-drama`、`ViMax` 的提示词模板里都有"参考图优先于文字描述"的约定，
但没人把它做成硬约束。实践中的两个真实烧钱点：

1. 提示词写到 3000 字，模型只读前 1500 字 —— 后半段纯浪费，还可能引入矛盾。
2. 给了角色参考图，文字又描述一遍"发型凌乱、脸型瘦削" —— 图文打架，出图反而更像"平均脸"。

`PromptBudget.audit()` 三类告警：

| 代码 | 条件 |
|---|---|
| `PROMPT_OVER_BUDGET` / `PROMPT_NEAR_BUDGET` | 字符数超/接近 `PROMPT_MAX_CHARS`（默认 1500，可环境变量覆盖） |
| `REF_OVERLOAD` | 同框参考图 > 3 张 |
| `REF_DESCRIBE_CONFLICT` | 有 `character` 参考图时，正文仍出现身体/五官描述词 |

编译期（`PromptCompiler.compile`）对图片/视频产物做审计，`warningLines()` 并入
`compile_warnings`，预算快照 `budget` 随产物落到生成记录（`generate.budget`），
前端能在产物详情里看到"这条提示词花了多少预算、哪一项踩线"。

## 八、明确不做的

| 想法 | 为什么不做 |
|---|---|
| 引入 `shanyin-director-master` 的代码 | 它是 Skill + Markdown 模板，没有服务端可调用接口；照搬等于把创作流程绑死在终端里 |
| 接 `ManjuForge` 的 22 项一致性检查 | 与本项目五维守卫重叠度高，重复实现只会让报错更难读；仅用来**对照确认无遗漏** |
| 用 LLM 直接生成时长 | 时长必须可复现、可解释。同一份 plan 重跑得到不同的秒数，等于没有 plan |
| 让 brief 也走 LLM | 定调一旦随机，下游全链路跟着漂。brief 是**规则推导**，确定性优先 |
